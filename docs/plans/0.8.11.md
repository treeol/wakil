#### Block 3 — Chromium handshake EOF after the port file is ready

- The docker/session launcher (internal/browser/launch_docker.go:163-223)
  starts Chromium with --remote-debugging-port=0 (line 160, ephemeral port
  chosen by Chromium), polls DevToolsActivePort (waitDevToolsPort, 229-245,
  150 ms, bounded by launchTimeout 30 s from launchSession), then opens the
  loopback tunnel (startTunnel, internal/browser/tunnel.go:77-86: listens on
  127.0.0.1:0, ephemeral host port; every connection spawns one
  `docker exec … python3 -c forwarder` inside the container, tunnel.go:114-
  152). lifecycle.go:156-167 then does ONE chromedp.Run(Navigate) with no
  retry: any EOF on the websocket handshake fails the launch with
  "cannot connect to Chromium at %s (%w)".
- The port is already ephemeral at both ends, which disproves the
  fixed-port theory: no fixed port exists anywhere in the browser path
  (grep for 15005 finds only the failing log line; the listener is
  net.Listen("tcp4", "127.0.0.1:0") at tunnel.go:78). 15005 is an
  unusual draw from the host's ephemeral range but is explained by that
  range on this host; the structural fact (port 0 at both ends) is what
  the fix relies on, not the range.
- The test runs the same browser path: integration_test.go:1182-1203
  wraps the hisn backend in exec.NewBackendExecutor and calls
  browser.NewManager + bm.Navigate, which goes through launchSession
  (lifecycle.go:134-168) and the session launcher (launch_docker.go:44-
  71) and the tunnel (tunnel.go:77-86). Same code, not a different one.
- The observed port 127.0.0.1:15005 IS the tunnel's ephemeral port. The EOF
  on the handshake means the first tunnelled connection reached the
  listener but the in-container forwarder chain (host listener → docker
  exec → python3 → Chromium socket) closed before Chromium answered — a
  transient transport race (forwarder spawn, exec startup, Chromium not
  yet accepting), not a stale-process or port conflict. tunnel.go:128-
  130 drains forwarder stderr to io.Discard, so a forwarder-side failure
  is invisible today; the fix keeps the drain but the retry is what
  protects the launch.
- The existing test failure (.tmp/host-verify/.../go-test.log:34) shows
  exactly this: Navigate → cannot connect to Chromium at
  http://127.0.0.1:15005 → EOF on the handshake request. The launch is
  single-shot: one transient EOF = failed test. Re-run passes because the
  race is timing-dependent.
- Local mode (launch_local.go:120-183) uses remote-debugging-pipe, no TCP
  port at all, and a 15 s bound. It has the same single-shot shape (one
  chromedp.Run, 173), so it gets the same readiness treatment.

### Verified findings

#### Block 1 — token-limit recovery

The length case is handled in exactly one place: `proxy.Client.Stream`
(internal/proxy/client.go:1702-1788). It returns `ErrBackendFatal` in three
shapes, discarding everything that streamed:

- client.go:1707-1709 — `finish_reason == "length"` with no content and no
  tool calls (reasoning-only exhaustion);
- client.go:1752-1760 — `finish_reason == "length"` with a tool call whose
  arguments are not a valid object (cut arguments);
- client.go:1785-1787 — `finish_reason == "length"` with complete-valid tool
  calls (trailing-content exhaustion).

The caller is `streamTurn` (internal/agent/turn_phases.go:156): at line 324
it calls `a.Client.Stream(...)`; on error it records failed-stream cost and
returns immediately (lines 325-328). Any `ErrBackendFatal` from the proxy
therefore ends the turn. The user-visible error the brief quotes
(`sessionhost: fatal backend request error: backend fatal error: model hit
token limit (finish_reason=length) — …`) is produced by
`hostTurn.run` (internal/wiring/hostturn.go:491-499): `DriveTurnWithResilience`
returns the error, and because it wraps `ErrBackendFatal`, hostturn wraps it
in `sessionhost.ErrBackendFatal`, which the host emits as a
`SessionError{request_error}` event. The headless consumer
(`consumeTurnEvents`, internal/wiring/headless.go:758) maps `request_error`
to `ExitError` (3, line 814) and emits `{"type":"error","message":…}`
(headless.go:507-508), and `--result-json` maps `ExitError` to
`exit_reason="error"` (internal/wiring/resultjson.go:74, test at
resultjson_test.go:110).

What is NOT discarded today: the streamed text is on screen (the sink fired
as chunks arrived), but it is not in `a.Conv`, so the saved session loses
it. The fix is therefore a narrow change at the proxy return (keep the text,
drop the cut tool call) plus a bounded retry of the turn at the agent layer
(one continuation per turn), plus a typed marker so a second cut is
distinguishable from a first. A tool call whose arguments were cut off must
never be executed — the proxy already checks argument validity
(client.go:1773-1781); the new path keeps the valid calls and drops only
the invalid ones, and the existing integrity check still rejects anything
that is not a valid object.

Reproduction before the change: a fake SSE server returning
`finish_reason="length"` with partial text currently yields `ErrBackendFatal`
and the text is lost (pinned by
`TestStreamLengthFinishWithCompleteToolCall`,
internal/proxy/stream_integrity_test.go:152-166, and the empty-content case
at client.go:1707). The new tests must show the text preserved.

The "stop with one clear line" target already exists in shape: today's error
message names the config key (`endpoints.<name>.max_tokens`). The new
second-cut line must additionally name the endpoint and the current
`max_tokens` value, which the endpoint config carries
(`Client.MaxTokens *int`, client.go:607; the endpoint name is
`Cfg.EndpointName`, saved into `Session.EndpointName` at session.go:25 and
app.go:996). The client itself does not know the endpoint name, so the line
is built at the agent layer where both `Cfg.EndpointName` and
`Client.MaxTokens` are visible.

Headless contract: a second cut is not a request error — it is a turn that
ran out of budget. The right code is `ExitIncomplete` (5,
headless_continuous.go:43, only returned for `--continue` today) or a new
outcome string. The terminal record must say what happened: today
`backend_failure` records carry `message` + `resume_id`
(headless.go:500-506); the second-cut record carries the same fields with a
distinct `outcome` so `--result-json` can map it. `exit_reason` in
`--result-json` gains a `token_limit` value.

#### Block 2 — loaded modules survive /resume

Modules are loaded through `ModuleRegistry.LoadModule`
(internal/agent/modules.go:478-493), which sets `r.loaded[name] = true`
under `r.mu`. `LoadedNames()` (modules.go:551-561) returns the loaded names
sorted by registry order. Nothing persists them: `Session`
(internal/agent/session.go:22-54) has no loaded-modules field, and
`SaveSession` (internal/agent/app.go:958-1054) snapshots collapse, prune and
cost state but no module state. On resume, `InstallSession`
(internal/agent/app.go:1100-1132) restores the transcript, workflow and cost
rows into a fresh App — the registry is rebuilt from scratch by
`BuildToolsWithModules` (modules.go:575-576), so every module starts
unloaded and the model must re-`load_module` everything.

The precedent for re-delivery exists: `mcpPreloadPair`
(modules.go:830-875) builds a synthetic `load_module` conversation (an
assistant message with a `load_module` call and a pinned `role:"tool"`
result, `Turn: -1`) for modules pre-loaded at session start. It is appended
after `ensurePreamble` in `SendOutcome` (app.go:1317-1329), stamped
`Turn: 0` so turn-span computation skips it. A resumed session's first turn
is also a "first turn" in the `preambleDay == ""` sense
(app.go:1300-1302; `InstallSession` resets `preambleDay` at app.go:1130), so
the same delivery mechanism can serve the resume path.

A module saved in the session may not exist on resume — an MCP server may
not be connected any more. `ModuleRegistry` already distinguishes that:
`LoadModule` returns `module %q: MCP server is not connected` for a
disconnected module (modules.go:485-487), `IsDisconnected` (451-456) reports
it, and `ModuleSchemasBlock` (788-796) returns false for an unknown name.
`PreloadModules` (759-771) likewise skips unknown/disconnected names. The
missing piece is the user-visible notice naming the dead modules — one
notice, appended to the next tool result like the late-connect
announcement (`pendingModuleAnnouncements`, app.go:69-72, consumed at
modules.go:1038-1042).

The persistence shape follows the existing precedent: a new `omitempty`
field on `Session` (like `CostRows`, session.go:53) written by
`SaveSession` and read by `InstallSession`. Old sessions (saved by v0.8.10)
have no such field and must resume identically to today: no modules, no
notice, no pair.

Reproduction before the change: with the switch on, load a module, save the
session, load it back into a fresh App — `IsLoaded` is false for every
module. The new test pins that the names are restored.

### Touched functions by name

Block 1:

- `Client.Stream` (internal/proxy/client.go:1152) — on `finish_reason =
  "length"`: keep the streamed content, drop tool calls whose arguments are
  not a valid object, and return the partial message with a typed marker
  (a new exported `ErrTokenLimitPartial` sentinel, wrapped) instead of
  `ErrBackendFatal`. The empty-content case (1707-1709) is the only shape
  that still ends the request with an error — there is nothing to keep — and
  it keeps today's message. The three `ErrBackendFatal` sites at 1707, 1756
  and 1786 change; the integrity check at 1773-1781 is unchanged, so a cut
  tool call is never executed.
- `streamTurn` (internal/agent/turn_phases.go:156) — when `Client.Stream`
  returns the typed token-limit marker: append the partial turn to `Conv`
  (text kept, cut call already dropped), append one user continuation
  ("Continue from where you stopped"), and make exactly one more request.
  If that request also ends at the limit, return a `TokenLimitError`
  naming the endpoint (`Cfg.EndpointName`), the model (`Client.Model`), the
  current `Client.MaxTokens` value and the `endpoints.<name>.max_tokens`

  loop cannot spin.
- `DriveTurnWithResilience` (internal/agent/resilience.go) — thread the new

- `ResultJSON` exit-reason mapping (internal/wiring/resultjson.go:74) —
  `ExitIncomplete` under this outcome maps to `exit_reason="token_limit"`.
- `hostTurn.run` (internal/wiring/hostturn.go:491-499) — the
  `ErrBackendFatal` classification is narrowed so the token-limit marker is
  not wrapped as a fatal request error; the new error type flows to the

### Open risks

- Block 1 changes the proxy's contract: `Stream` may now return a message
  with a wrapped marker error where it returned `ErrBackendFatal` before.
  Any other `Stream` caller (compact, side-question, prune rater — all
  through `Client.Stream`) must not treat the marker as a fatal request
  error; the marker is only acted on by `streamTurn`, and every other
  caller fails exactly as it does on `ErrBackendFatal` today.
- The continuation request costs a second call at the same `max_tokens`;
  the total output can exceed the endpoint budget by one request. That is
  the requested behaviour (recover, then stop), and the spend is one call.
- A resumed module re-delivery appends a pair to `Conv`; the tool array
  does not change, so the prompt-cache contract holds. The pair adds bytes
  to the first resumed request; it is the same bytes a fresh
  `load_module` would add, plus no round trip.
- `LoadedModules` is written only with the switch on. A session saved with
  the switch on and resumed with it off keeps the field in the file but no
  module is loaded (the registry is nil, so `InstallSession` skips it) —
  the field is inert data, never a request change. With the switch off on
  both sides, no field is written and requests stay byte-identical to
  v0.8.10.
- The second-cut headless code changes from `ExitError` (3) to
  `ExitIncomplete` (5); scripts that switch on the exit code must learn the
  new value (CHANGELOG states it).
