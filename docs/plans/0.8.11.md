#### Block 3 — Chromium handshake EOF after the port file is ready

- The docker/session launcher (internal/browser/launch_docker.go:163-223)
  starts Chromium with --remote-debugging-port=0 (line 160, ephemeral port
  chosen by Chromium), polls DevToolsActivePort (waitDevToolsPort, 229-245,
  150 ms, bounded by launchTimeout 30 s from launchSession), then opens the
  loopback tunnel (startTunnel, internal/browser/tunnel.go:77-86: listens on
  127.0.0.1:0, ephemeral host port; every connection spawns one
  `docker exec … python3 -c forwarder` inside the container, tunnel.go:114-
  152). lifecycle.go:156-167 then does ONE chromedp.Run(Navigate) with no
  retry: any EOF on the websocket handshake fails the launch with
  "cannot connect to Chromium at %s (%w)".
- The port is already ephemeral at both ends, which disproves the
  fixed-port theory: no fixed port exists anywhere in the browser path
  (grep for 15005 finds only the failing log line; the listener is
  net.Listen("tcp4", "127.0.0.1:0") at tunnel.go:78). 15005 is an
  unusual draw from the host's ephemeral range but is explained by that
  range on this host; the structural fact (port 0 at both ends) is what
  the fix relies on, not the range.
- The test runs the same browser path: integration_test.go:1182-1203
  wraps the hisn backend in exec.NewBackendExecutor and calls
  browser.NewManager + bm.Navigate, which goes through launchSession
  (lifecycle.go:134-168) and the session launcher (launch_docker.go:44-
  71) and the tunnel (tunnel.go:77-86). Same code, not a different one.
- The observed port 127.0.0.1:15005 IS the tunnel's ephemeral port. The EOF
  on the handshake means the first tunnelled connection reached the
  listener but the in-container forwarder chain (host listener → docker
  exec → python3 → Chromium socket) closed before Chromium answered — a
  transient transport race (forwarder spawn, exec startup, Chromium not
  yet accepting), not a stale-process or port conflict. tunnel.go:128-
  130 drains forwarder stderr to io.Discard, so a forwarder-side failure
  is invisible today; the fix keeps the drain but the retry is what
  protects the launch.
- The existing test failure (.tmp/host-verify/.../go-test.log:34) shows
  exactly this: Navigate → cannot connect to Chromium at
  http://127.0.0.1:15005 → EOF on the handshake request. The launch is
  single-shot: one transient EOF = failed test. Re-run passes because the
  race is timing-dependent.
- Local mode (launch_local.go:120-183) uses remote-debugging-pipe, no TCP
  port at all, and a 15 s bound. It has the same single-shot shape (one
  chromedp.Run, 173), so it gets the same readiness treatment.

### Open risks

- Block 1 is Breaking: users relying on config host_work_dir lose their
  folder. The one-line warning mitigates but cannot preserve behaviour.
  Sandbox trust is keyed on the folder path, so starting in a new folder
  may ask for trust again — acceptable per the brief, never granted by
  Wakil itself. A bare `wakil` from $HOME or / now bind-mounts that
  folder (today's `wakil .` behaviour); non-interactive launches (cron,
  launchers) get the cwd folder with no interactive trust prompt possible
  — they keep working with the cwd as workspace, which IS the requested
  behaviour, but it is a behaviour change for scripted launches too.
  The warning fires on every interactive start while the ignored key is
  set (same as the existing WAKIL_WORKSPACE_PATH line); it is one line.
- Block 1: store keys do NOT move for a given launch cwd (verified: the
  stores already follow cwd; only the sandbox mount/cwd was divergent).
  Old sessions are never deleted or rewritten (byte-identical) and stay
  reachable via --resume --all (test added).
- Block 1: host_work_dir also feeds the docker bind mount; removing it from
  workspace resolution must not break the mount for the resolved
  workspace. The positional arg already drives the mount today, so the
  unified path keeps that; the config-template check: config.example.json
  and `wakil init` never write host_work_dir, so a default config cannot
  trigger the warning (verified by grep).
- Block 2: headless output is one notice line; the styled (ANSI) branch
  only applies on a real terminal (already the case for the existing
  notices). VOID / NOT COMPLETED lines become dim.
- Block 3: readiness polling adds up to launchTimeout latency on a
  live-but-unanswered browser (dead process fails on the early probe);
  the bound is named in the error. The retry reduces, and may not
  eliminate, the flake — the 20-run result is reported as observed
  behaviour, with the fault-injection test as the rate-independent
  acceptance.
