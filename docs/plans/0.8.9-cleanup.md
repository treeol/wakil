### Block 5 — sed brackets (CONFIRMED; design below)

## B6. Mashūra plan review (op-4, three panel members; opinions, checked by me)

Question put: what in this plan is wrong, unproven or risky, and what would an agent still lose after a collapse with the block 7 design?

### Taken (BLOCKING; the design above is amended as follows)

- **Block 5 — three-mode agreement dropped; one stricter rule instead.** Reviewers (all three) showed that `]`-first (`[]/]`, `[^]/]`), `[:class:]`/`[.x.]`/`[=x=]` and a delimiter inside a bracket make a "close at first `]`" mode agree with the wrong parse. Verified by me: `sed 's/a/b\/;#/w out' f` really writes `out` (GNU sed 4.9, temp dir), and today's classifier says `D=true` for it (the `;` is split first). Amended rule: a bracket expression is accepted only in an address regex or the `s` pattern, only when its body is plain: the first body character is not `]` or `^]`, the body has no `[`, no backslash, no delimiter character, and a closing `]` exists. Anything else (any of `[]`, `[^]`, `[[`, `[:`, `[.`, `[=`, a bracket in a replacement-free position the parser cannot place, `[` or `]` as delimiter, unterminated) stays destructive. Plain bodies parse the same in every sed, so no multi-parser argument is needed. In the replacement part `[` is literal in every sed and is skipped by the existing delimiter scan.
- **Block 5 — quoting.** `sedArgsDestructive` only gets unquoted arguments, so the quote check is made at the two call sites that hold the raw tokens (`IsDestructiveShell`, `IsReadOnlyShell`): an argument that contains `[` must be wrapped in single quotes with no other `'` inside; double-quoted, unquoted, `-e'…'`-attached and `--expression=…` forms stay destructive/not read-only (accepted false positives). Side effect, stated: `sed -n p 'f[1]'`-style file arguments with `[` must also be single-quoted to stay read-only. Acceptance: `D=false` and `RO=true` for the allowed rows; v0.8.5 corpus has no `sed` rows (grep count 0), so the golden file is not touched and not edited.
- **Block 5 — evidence the exec test must show.** The allowed forms are run under GNU sed 4.9 in a temp dir (no file created); the forbidden bracket+`w` forms are table rows only (they are never run). If the quoted-token change is not small at both call sites, block 5 is dropped and reported.
- **Block 7 — claims narrowed.** Ranges are labelled "requested" (`read (requested)`), because no result bytes are read, so truncation or EOF is not visible; a read entry is dropped when a later write/edit of the same path is in the range (the file changed). Command name: leading `cd x &&` segments and `VAR=value` words are skipped, so `cd x && go test` yields `go`. "Merge" is stated honestly: the part is **recomputed over the cumulative range** from the raw `Conv` (one part, never nested), and a second collapse can evict first-range entries under the 1500-byte cap; a test where range 1 alone fills the cap pins this. The guarantee is "no direct tool-result copy": assistant text can quote tool output, so the report says so.
